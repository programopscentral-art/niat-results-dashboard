03 · Data model

Your wide sheet, flattened into a schema that scales.

Subject counts and column layouts differ across colleges (some have “Name”, others “BITS ID”; Aurora even splits into Term-I / Term-II). So results are stored one row per student-per-subject — flexible, queryable, and future-proof for new semesters.

C

colleges

Registry of real tabs. Junk/template tabs never enter here.

S

semesters

One per batch·semester spreadsheet. Aurora terms live here.

👤

students

Keyed by UID — persists across every semester.

Σ

results

Per subject: internal, external, total, pass/fail.

supabase/migrations/0001_core.sql
-- A student is stable across semesters; identity keyed by NIAT UID
create table students (
  id            uuid primary key default gen_random_uuid(),
  uid           text unique not null,      -- N25H02B0198
  full_name     text,
  university_id  text,                    -- 2025EB01894 (dirty-ID normalized)
  bits_id       text,
  college_id    uuid references colleges(id),
  status        text default 'active',     -- active | flagged | withdrawn
  created_at    timestamptz default now()
);

-- Subjects vary per college & semester → positional + named
create table subjects (
  id           uuid primary key default gen_random_uuid(),
  semester_id  uuid references semesters(id),
  college_id   uuid references colleges(id),
  position     int,                     -- 1..8 (sheet column group)
  name         text,
  unique (semester_id, college_id, position)
);

-- The heart: one row per student per subject. Nulls = not yet entered
create table results (
  id           uuid primary key default gen_random_uuid(),
  student_id   uuid references students(id),
  semester_id  uuid references semesters(id),
  subject_id   uuid references subjects(id),
  internal_pct numeric(5,2),
  external_pct numeric(5,2),
  total_pct    numeric(5,2),
  passed       boolean,                 -- normalized from Pass/Fail/P/F/blank
  unique (student_id, semester_id, subject_id)
);

-- Denormalized per-student summary → dashboards read ONE fast row
create table result_summaries (
  student_id      uuid references students(id),
  semester_id     uuid references semesters(id),
  total_cgpa      numeric(4,2),        -- 7.94
  total_pct       numeric(5,2),
  subjects_failed int,
  overall_passed  boolean,
  data_complete   boolean,             -- false when subjects still blank
  primary key (student_id, semester_id)
);

-- Audit + change-detection: every raw sheet row hashed for diffing
create table sync_rows (
  semester_id uuid, college_id uuid, uid text,
  row_hash text, raw jsonb, deleted_at timestamptz,
  primary key (semester_id, college_id, uid)
);

Indexes on results(student_id), results(semester_id, subject_id, passed), and students(college_id) keep “who failed subject X” queries instant even at full scale.

04 · The sync engine — cron-only & fully dynamic

Share a sheet. It shows up. No setup, ever.

One loop, every 60 seconds, does everything — discovery, change-detection, and sync — so onboarding a new semester means simply sharing its spreadsheet with the service account. Nothing else to configure per sheet.

1

Discover

Lists spreadsheets shared with the service account whose title matches Batch YYYY · Semester N, and auto-registers new ones — tabs matched to colleges automatically.

→ New semester = one share action.

2

Skip unchanged

Compares each file’s Drive modifiedTime to the last one seen. Untouched sheets are skipped with a single cheap metadata call — no wasted reads, quota-safe at scale.

→ Idle sheets cost almost nothing.

3

Sync changed

Reads all tabs of a changed sheet in one batched call, diffs by row-hash, upserts only changed rows. Supabase Realtime streams them to open dashboards.

→ ≤ ~60s edit-to-screen.

Updates

Changed row-hash → upsert → the exact cells change on screen, in place, highlighted.

Deletes

Row vanishes from the sheet → absent in diff → soft-deleted (deleted_at) → removed from UI, kept for audit.

New rows / colleges

New UID → inserted. A brand-new tab is auto-registered as “pending” and ops is notified before it goes live.

05 · Scaling to 1–2k users

Reads are cheap. We keep them that way.

DB

Pooled connections

Supavisor pools thousands of clients onto a small Postgres pool — no connection exhaustion.

⚡

Scoped realtime

Each viewer subscribes only to their college’s rows, so 2k users ≠ 2k× fan-out.

▦

Materialized summaries

The dashboard reads one summary row per student, not eight joins.

◐

Edge cache

College lists + static shells cached on Vercel’s CDN; only live rows hit the DB.

API

Quota-safe sync

Only dirty tabs are read; hashing skips no-op writes → far under Sheets API limits.

Q

Queued ingest

BullMQ serializes bursts of edits so a busy results day never overwhelms writes.

▲

Batch imports

First-time backfill of a semester runs as a bulk COPY, not row-by-row.

🔒

RLS at the row

Access is enforced in the database, so scaling users never widens the blast radius.

06 · Edge cases — found in your real data

The messy reality, already handled.

These aren’t hypotheticals — every one below is present in the current sheet. The pipeline treats data quality as a first-class feature: normalize what’s safe, flag what isn’t, never silently corrupt.

1

Junk & template tabs

Sheet10/11/12 and “{University_Copy this sheet…}” exist. Fix: only tabs in the college registry are ingested.

2

Dirty University IDs

2025EBO1998 (letter O), 2025EB2034 (missing digit). Fix: normalize + flag anomalies for ops review.

3

Sparse rows

Many students have only UID + CGPA; subjects blank. Fix: partial results allowed, marked “in-progress”, not failed.

4

Varying columns

Some tabs use “Name”, others “BITS ID”. Fix: per-college header mapping, auto-detected on ingest.

5

Multi-term tabs

Aurora has Term-I & Term-II. Fix: term modeled on the semester, one college → many term-sheets.

6

Row reordering

Ops sort the sheet constantly. Fix: rows keyed by UID, never by position — reorders are no-ops.

7

Renamed / deleted tabs

A tab rename would orphan data. Fix: track by stable college code; alert ops on rename, keep last-known data.

8

Pass/Fail spelled many ways

“Pass”, “P”, “Fail”, blank. Fix: normalized to a strict boolean enum on write.

07 · Delivery roadmap

From this blueprint to production.

Foundation Week 1

Supabase schema + RLS, college registry seeded from the 19 live tabs, Next.js app shell deployed to Vercel.

Ingestion Week 1–2

Railway sync worker: Sheets API reader, header-mapping, row-hash diffing, validation + anomaly flags, first full backfill.

Real-time Week 2

Apps Script onChange bridge + HMAC webhook, Realtime subscriptions, 60s reconciliation cron. Edit-to-screen proven end-to-end.

The dashboard Week 2–3

Colleges grid → college view → student drill-down: subject-wise backlogs, pass/fail, CGPA, filters, search, exports.

Hardening & scale Week 3–4

Auth roles, load test to 2k, monitoring & sync-health alerts, ops anomaly console. Ready for the next semester’s sheet — drop it in, it flows.
